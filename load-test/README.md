# ISDP realtime load test

This toolkit reproduces the optimized Firebase traffic generated by the Flutter app. Each virtual user:

- signs in with Firebase Authentication;
- reads its profile and the user directory;
- opens the role-filtered work-order listener shared by data and sync status;
- opens small per-job and total `chat_unread` listeners;
- performs occasional workflow and chat writes; and
- records latency, errors, snapshot activity and observed realtime propagation.

It is deliberately not a generic HTTP benchmark. The Firebase client SDK is used so Authentication, Firestore Security Rules and long-lived snapshot listeners are exercised.

## Safety

The scripts refuse production-like projects by default. A project must use a name containing `test`, `staging`, `load` or `demo`, or its exact ID must be supplied in `LOAD_TEST_ALLOW_PROJECT`.

Use a dedicated billed staging Firebase project in the same region as production. Never put real notification tokens in its test-user documents. Seeding new work orders fires deployed Firestore triggers, so either seed before deploying Functions or intentionally include those invocations in the staging-cost budget.

The Firebase Emulator Suite is useful for checking the scenario and Security Rules, but it does not reproduce production capacity, indexes or quotas. The final result must come from staging.

## Configure

Node.js 20 or newer is required.

```powershell
cd C:\dev\ISDP\load-test
Copy-Item .env.example .env
npm install
```

Edit `.env` with the staging web-app values from Firebase project settings. `seed` and `cleanup` also require an absolute `GOOGLE_APPLICATION_CREDENTIALS` path for a staging service account.

Check configuration without contacting Firebase:

```powershell
npm run seed -- --users 500 --orders 5000 --dry-run
npm run load -- --users 500 --shards 5 --shard 0 --ramp 15 --duration 45 --dry-run
```

## Seed realistic data

The default role mix is 5% administrators, 15% supervisors and 80% technicians.

```powershell
npm run seed -- --users 500 --orders 5000 --messages-per-order 2 --run-id baseline-500
```

The seed is deterministic and can be rerun. Test users are `loadtest-000000` onward and work orders are `loadtest-order-0000000` onward.

## Run 500 users

Use five machines or containers. Copy the same `load-test` directory and `.env` to each, then start one shard on each machine at approximately the same time:

```powershell
# Machine 1
npm run load -- --users 500 --shards 5 --shard 0 --ramp 15 --duration 45

# Machine 2
npm run load -- --users 500 --shards 5 --shard 1 --ramp 15 --duration 45

# Machine 3
npm run load -- --users 500 --shards 5 --shard 2 --ramp 15 --duration 45

# Machine 4
npm run load -- --users 500 --shards 5 --shard 3 --ramp 15 --duration 45

# Machine 5
npm run load -- --users 500 --shards 5 --shard 4 --ramp 15 --duration 45
```

Each process is limited to 125 users by default. This avoids mistaking a saturated load-generator laptop for an application failure.

Important options:

| Option | Default | Meaning |
| --- | ---: | --- |
| `--users` | 500 | Total users across all shards |
| `--shards` | 5 | Number of distributed processes |
| `--shard` | 0 | Zero-based shard number |
| `--ramp` | 15 | Minutes over which users connect |
| `--duration` | 45 | Steady-state minutes after ramp-up |
| `--chat-listeners` | 3 | Jobs with message/read listeners per user |
| `--workflow-rate` | 0.05 | Workflow writes per user per minute |
| `--chat-rate` | 0.02 | Chat writes per user per minute |

For a login-storm test, repeat with `--ramp 2 --duration 15`. Do this only after the gradual test passes.

Reports are written under `reports/` as JSON. Compare these measurements with the Firebase console's Firestore Usage and Cloud Functions metrics; only Firebase billing/usage data is authoritative for charged reads.

Suggested pass criteria:

- `auth.p95Ms` below 2,000 ms;
- `initialDashboard.p95Ms` below 5,000 ms;
- `workflowWrite.p95Ms` below 1,500 ms;
- `realtimePropagation.p95Ms` below 2,000 ms;
- error rate below 1%; and
- no sustained Function errors, retries or uncontrolled read costs.

## Emulator smoke test

Set the emulator variables in `.env`, start the Firebase emulators from the repository root, then seed and run a short test:

```powershell
cd C:\dev\ISDP
firebase emulators:start --only auth,firestore

cd C:\dev\ISDP\load-test
npm run seed -- --users 25 --orders 50 --messages-per-order 1 --run-id emulator-smoke
npm run load -- --users 25 --shards 1 --shard 0 --ramp 0.1 --duration 1 --run-id emulator-smoke
```

## Cleanup

Cleanup removes only deterministic load-test users and work orders carrying the selected run ID. It recursively deletes message and read subcollections. The confirmation flag is mandatory.

```powershell
npm run cleanup -- --users 500 --run-id baseline-500 --confirm
```
